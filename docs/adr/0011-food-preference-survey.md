# Derive Soft Preference tags from a pairwise onboarding survey, not just free text

Until now the only way to populate `liked_tags`/`disliked_tags` was two free-text boxes on `PreferencesForm` (`liked_foods_text`/`disliked_foods_text`), LLM-parsed by `app/services/preference_parsing.py`. That's a blank-page problem for a brand-new user with no dining hall history yet, and in practice yields very few tags — most people type two or three words. It also depends on an LLM call succeeding to produce any signal at all.

We considered a Likert-style rating list (rate each of N staple dishes 1-5), but that's slower to complete and produces noisier signal than a direct comparison — a 1-5 scale means different things to different people, while "which of these two would you rather eat" is unambiguous and fast. We also considered generating survey items from whatever happens to be on today's live-scraped menu, but that makes the survey non-reproducible run to run and complicates picking deliberately *contrasting* pairs (comfort vs. healthy, plant vs. animal protein, etc.) — instead we hand-curated a fixed catalog of real, currently-served Cornell dining item names (cross-checked against the live `menu_items` table) in `app/services/food_survey.py`, each hand-tagged with the same short lowercase taste-tag vocabulary `preference_parsing.py` already produces.

Decision: onboarding gains a 10-round forced-choice "which would you rather eat" survey (plus a skip option per round), served only after `PreferencesForm` has saved `diet_restrictions`/`allergens`, so `app/services/food_survey.py::build_survey` can filter out pairs containing an item the user can't eat — it draws from a 16-pair pool (10 primary + 6 backup) so a restricted user still gets close to 10 valid rounds, degrading gracefully (never erroring) if fewer are available. Each round's winning item's tags get +1, the losing item's tags -1 (`score_survey`); tags with positive net become `liked_tags`, negative net become `disliked_tags`, merged (deduped, union) directly into the *same* `UserPreference.liked_tags`/`disliked_tags` fields free-text parsing already writes (`merge_tags`) — not a parallel column or a second scoring path. That means `app/services/preference_scoring.py` and `app/routers/crafted_meals.py` need zero changes to pick up survey-derived signal; see [[CONTEXT.md]]'s Soft Preference definition and [[0009-deterministic-preference-preranking]] for how those tags get used. A tag that ends up liked from one source and disliked from another resolves as liked.

Completion is tracked via `UserPreference.food_survey_completed`, added with no backfill default — existing users, not only new signups, are prompted once on their next login. Retaking the survey (available anytime from the crafted-meals/diary header) is additive: it unions new signal onto whatever's already there rather than resetting prior survey-derived tags first, since doing the latter would require tracking which tags came from the survey versus free text — deferred until there's evidence users' tastes are actually flipping. Similarly, changing `diet_restrictions`/`allergens` after completing the survey does not re-trigger it, so a now-incompatible item's tags can linger; low-severity since Soft Preferences only ever rank candidates, never filter them ([[CONTEXT.md]]).
