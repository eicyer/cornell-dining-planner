# Add a same-origin admin panel for correcting NutritionMatch/DietTag by hand

`NutritionMatch` and `DietTag` ([[0001-nutrition-data-source]], [[0002-enrichment-pipeline]]) are keyed by exact `item_name` and shared globally across every eatery/date that happens to serve an item under that name — a single bad USDA match or LLM estimate is wrong everywhere at once, not just for one menu appearance. Until now, the only way to fix one was a direct database shell session, which doesn't scale as an ongoing "spot mistakes as they show up in the app" workflow.

We considered two other ways to gate a fix-it UI:

- **A screen inside the Expo app**, gated to only render for one account. Rejected: this is a single-operator internal tool with no reason to run on a phone, and the web build would need cross-origin cookie handling against the FastAPI session that a same-origin page avoids entirely. Building a dense, searchable data table in React Native is also strictly harder than plain HTML/CSS for no payoff here.
- **A `role`/`is_admin` column on `User`**, the conventional multi-admin pattern. Rejected as unnecessary: exactly one operator (`emiricyer07@gmail.com`) will ever use this, so a single `admin_email` setting (`app.core.config.Settings`) checked against `User.email` is simpler and needs no schema change. Revisit if a second operator is ever added.

Decision: a new `/admin` route served directly by FastAPI, same origin as the API, reusing the existing Google-OAuth session cookie (`app.routers.auth`) with no CORS involved. `GET /admin` renders one of three Jinja2-templated pages depending on session state (not logged in / wrong account / the admin account — see `app.routers.admin_pages`), and a separate `app.routers.admin_api` router (prefix `/admin/api`) exposes the actual list/detail/update JSON endpoints behind `app.core.deps.get_current_admin`, independent of the page-level check. `/auth/login` gained a safelisted `?next=/admin` param (and `/auth/callback` honors it) so completing Google sign-in from the admin page lands back on `/admin` instead of the mobile app's `frontend_url` — purely additive, the existing Expo login flow never sends `next` and is unaffected.

Editable fields are exactly what already exists on `NutritionMatch`/`DietTag`: the six per-100g macros, `source`, `confidence_score`, `diet_tags`, `likely_allergens`. Portion size stays **read-only** in this panel: it was never persisted per-food by design ([[0007-nutrition-per-100g-portion-deferred]]) and remains a client-only keyword heuristic in `frontend/foodDensity.ts`. `app.services.portion_display` is a manually-synced Python port of that file's `UNIT_RULES`, used only to show the admin which unit/grams-per-unit a food currently maps to — the same "keep in sync by hand" contract `frontend/api.ts` already keeps for this backend's vocab constants, just mirrored in the other direction. Fixing a bad portion keyword rule remains a code change to `foodDensity.ts`, not a data edit through this panel.

Consequence, documented as a known follow-up rather than fixed here: `app.jobs.enrich_items.find_unenriched_items` treats "`sugar_g_per_100g`/`fiber_g_per_100g` is non-null" as its only "already enriched" signal. An admin correction to an item that already has both is safe — the nightly cron skips it going forward. A correction to an item still missing sugar/fiber is not: the next cron run will still see it as unenriched and may silently re-run USDA/LLM enrichment, overwriting the manual edit (including the macros, since `save_result` upserts the whole row). A future `admin_edited_at`-style column the cron could check would close this gap; out of scope for this change.
