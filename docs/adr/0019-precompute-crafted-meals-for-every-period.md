# Precompute crafted meals for every meal period, not just "now"

[[0017-crafted-meals-caching]] cached `GET /menus/today/crafted` per `(user, date)`, computed lazily on whichever request hit it first each day. That request's wall-clock hour picked *one* meal period per eatery (`pick_meal_period`) and only that period's candidates got ranked/polished — the cached payload was frozen to whatever was "now" at cache-build time. A user who opened the app at 9am (Breakfast) and again at 6pm (Dinner) the same day got Breakfast both times, since the cache hit skipped recomputation entirely. This is what broke "show me dinner options — it's dinner time": the day's first request, whenever it happened to land, permanently decided the period for the rest of the day.

Root cause of *why* the cache was so often built at the wrong time: the 5am cron (`scripts/daily_refresh.sh`, via crontab) that was supposed to seed the day's menu data (and, indirectly, warm this cache) doesn't reliably run — crontab doesn't wake a sleeping Mac, so on a laptop that sleeps overnight the run is silently skipped more often than not (see the launchd migration below). The lazy per-request cache was masking that by quietly falling back to "whatever period matches whenever a human first asks."

Decision: `CraftedMealsCache.payload` now stores every meal period each eatery serves that day — `list[EateryDailyCraftedOut]`, each with a `periods: dict[meal_period, PeriodCraftedOut]` map (`app.routers.crafted_meals`) — instead of just the one period that was current at build time. `build_daily_crafted` runs the optimizer and both polish calls (`polish_meal` for the today-list's single pick, `polish_meals` for the eatery-detail options list) for *every* period, concurrently across periods and eateries via `asyncio.gather`. The two request handlers (`crafted_meals_today`, `crafted_meals_for_eatery`) no longer do any LLM work themselves — they just call `pick_meal_period`/`next_meal_periods` against the cached day's available periods and slice out the matching entry, so the period shown always matches *request* time, not whatever time the cache happened to be built.

A new job, `app.jobs.craft_daily_meals`, runs this precompute for every onboarded user (has a `UserPreference` row) and is idempotent — it skips users who already have today's row, same pattern as `scrape_menus`/`enrich_items`. `daily_refresh.sh` now runs it last (scrape → enrich → craft), so a normal cron run leaves every user's full day ready before anyone opens the app. The lazy per-request build (`get_or_build_daily_crafted`) stays as a same-day fallback for whenever the cron hasn't run yet — degrades to "slow once," not broken.

Cost tradeoff accepted: precomputing every period (not just "now") means the LLM polish step runs for periods nobody may check yet (e.g. Dinner candidates get built at 5am). Considered computing only "now" and having later requests fill in missing periods on demand instead; rejected because that reintroduces the original bug's shape (a request's own timing decides what gets cached) and reappears every time the cron is late, which is the exact case this change exists to make harmless.

Also fixed in the same change: `pick_meal_period` used `datetime.datetime.now()` (server-local time) rather than Ithaca time — the same bug `/menus/today`'s date lookup had, now shared as `app.core.clock.ithaca_now`/`ithaca_today`. A backend running in UTC (e.g. a cloud host) would otherwise pick the wrong meal period near Eastern midnight even with correct menu data loaded.

### Cron reliability (crontab → launchd)

The 5am refresh moved from a plain `crontab` entry to a `launchd` LaunchAgent (`scripts/com.cornell-dining-planner.daily-refresh.plist`) with several `StartCalendarInterval` windows through the morning (5am, 8am, 11am) instead of one. `launchd` still won't wake a sleeping Mac by itself — like `cron`, a missed window is just skipped, not queued — but multiple windows plus `RunAtLoad` (fires once whenever the agent loads, i.e. every login/restart) give a normal daily pattern of "asleep overnight, awake sometime in the morning" several chances to catch the refresh instead of one. Every job in the pipeline is idempotent, so redundant runs across windows cost nothing beyond a few no-op DB queries. For a machine that needs a guarantee rather than several chances, `pmset repeat wake` can schedule an actual hardware wake before 5am — left as a manual step (README) rather than automated here, since it's a machine-wide power-management change outside this project's scope to make unasked.
