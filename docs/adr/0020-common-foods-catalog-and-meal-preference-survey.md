# Add a persisted Common Foods catalog and a Meal Preference Survey built on it

Until now there was no stored notion of "what's a typical breakfast/lunch/dinner protein/vegetable/carb" — [[0012-plate-role-portioning]]'s `classify_role` only classifies items already on a *live* menu by nutrient density, and [[0011-food-preference-survey]]'s 10-round onboarding catalog is a small, hand-curated, Cornell-wide set of broad contrast pairs (comfort vs. healthy, plant vs. animal protein) with no meal-period structure and no way to compare *within* a food type — e.g. "for dinner specifically, chicken vs. fish vs. minced meat" or "for lunch, which salad style." Building that signal requires a reference catalog grouped by meal period and plate role, admin-visible the way [[0016-admin-panel-for-nutrition-corrections]] made `NutritionMatch`/`DietTag` admin-visible, rather than another set of Python constants nobody but a developer can see or edit.

Decision: a new `CommonFood` table (`app.db.models.CommonFood`) holds this catalog — `name`, `meal_period` (breakfast/lunch/dinner), `role` (protein/vegetable/carb, same vocabulary as [[0012-plate-role-portioning]]'s `ROLE_ORDER`), `subtype` (a short grouping key like `chicken`/`fish`/`minced_meat`/`caesar_salad`/`potato`), `tags` (substring-matchable human phrases, same contract as `FoodSurveyItem.tags`), `diet_tags`/`allergens` (compatibility filtering, same shape as the existing survey catalogs), and `active` (admin soft-delete, since a survey `pair_id` already handed to a client shouldn't 404 just because an admin retired a row). Seeded via an Alembic data migration rather than a runtime seed script — same "DB is the editable source of truth, migrations seed it once" pattern already established for schema + initial data elsewhere in this repo — and editable afterward through new `/admin/api/common-foods` CRUD routes plus a "Meal Catalog" tab on the existing `/admin` panel, gated by the same `get_current_admin` dependency as every other admin route.

`app.services.meal_preference_survey.build_meal_preference_survey` reuses [[0011-food-preference-survey]]'s `FoodSurveyItem`/`FoodSurveyPair` dataclasses and `score_survey`/`merge_tags` engine directly — same pattern [[0013-station-survey]] already established for a second pair source. It groups active, diet/allergen-compatible `CommonFood` rows into nine `(meal_period, role)` buckets, picks one representative item per distinct `subtype` within a bucket (alphabetically, for determinism), and pairs adjacent subtypes — capped at one pair per bucket, so the survey stays a quick ~9-round comparison (one round per meal-period × role combination) rather than exhaustively pairing every subtype. This is deliberately the same "quick, not exhaustive" ethos as [[0013-station-survey]]'s `MAX_PAIRS_PER_STATION`, tuned to 1 instead of 2 here since there are already nine buckets rather than three stations. Results merge into the same `liked_tags`/`disliked_tags` `UserPreference` fields via the same `merge_tags` union — a winning `chicken` tag already substring-matches "Grilled Chicken Breast" the same way any other tag does, so `app.services.preference_scoring` needs no changes to pick up this signal.

New endpoints `GET`/`POST /preferences/meal-preference-survey` mirror [[0013-station-survey]]'s endpoints exactly: no server-side state between the two calls (the POST re-derives the same pairs from the same `CommonFood` rows and resolves `pair_id`s against them), repeatable at any time from a "Refine Meal Preferences" entry point alongside the existing "Retake Food Survey" link, and — like the Station Survey — never touches `UserPreference.food_survey_completed`.

## Known limitation

Because pairing picks one representative item per subtype rather than exhaustively comparing every item, a bucket with several items sharing a subtype (e.g. dinner vegetable's Broccoli/Green Beans/Brussels Sprouts all tagged `roasted_veg`) only ever contrasts that subtype as a block, not the specific dishes within it. If per-dish (not just per-subtype) signal within a bucket turns out to matter, `MAX_PAIRS_PER_BUCKET` could be raised — deferred until there's evidence one pair per bucket isn't enough.
