# Rank crafted-meal candidates by rule-based preference fit before the LLM polish step

[[0003-meal-crafting-algorithm]] made the LLM the sole judge of Soft Preferences (liked/disliked foods) — it picks among candidates and, if the API call fails, falls back to an arbitrary candidate (index 0) with no regard for preferences at all. That's an acceptable failure mode for *ranking quality* but not for *whether preferences apply at all*: a rate-limited or slow request would silently drop every Soft Preference, including the newly added "prefer whole & minimally processed foods."

We considered leaving this as LLM-only and only hardening the failure path (e.g. skip polish and re-try), but that still leaves preference-fit entirely dependent on one LLM call succeeding *and* judging well — there's no deterministic floor.

Decision: `app/services/preference_scoring.py` scores every candidate deterministically (substring match on liked/disliked tags against item names, category/keyword penalty for "prefer whole & minimally processed foods") and sorts candidates by score before they reach `polish_meal`. The LLM still makes the final pick and writes the name/rationale — it's free to choose any candidate, not just the top-scored one — but its existing index-0 failure fallback now means "the best rule-based match" instead of "whatever came first," with no changes needed inside `meal_polish.py` itself. Deterministic scoring never excludes a candidate outright, matching [[CONTEXT.md]]'s definition of Soft Preference — a disliked food can still appear if nothing else fits the macro target, it's just ranked lower.
