# Track sugar and fiber alongside the existing four macros

Extending Soft Preferences beyond liked/disliked tags and "prefer whole & minimally processed foods" — starting with "less sugar" and "more fiber" — needs real per-item grams to score against, the same way [[0009-deterministic-preference-preranking]] scores whole-foods-ness off category/keyword heuristics today. Neither sugar nor fiber existed anywhere in the pipeline: not in `NutritionMatch`, not in the USDA fetch (`app/services/usda.py`), not in the LLM estimate fallback (`app/services/llm_enrichment.py`).

We considered estimating both from category/keyword heuristics the way [[0012-plate-role-portioning]]'s whole-foods penalty already does ("dessert" category, "candy"/"cookie" keywords ⇒ assume high sugar). Rejected: unlike whole-foods-ness, sugar and fiber are numbers USDA and the LLM estimate path can both report directly and cheaply — a heuristic would be strictly worse data for no savings.

Decision: add `sugar_g_per_100g` and `fiber_g_per_100g` to `NutritionMatch`, `UsdaMatch`, and `EnrichmentResult`, populated the same way the existing four macros are — taken directly from USDA when matched (fiber via nutrient ID 1079; sugar via 2000, falling back to the older SR-Legacy ID 1063 depending on which data tier matched, see `usda.py`), or LLM-estimated alongside calories/protein/carbs/fat when no USDA match exists. Both columns are nullable, unlike the four existing macros: they were added after every existing item was already enriched, so old rows start out without them. `app/jobs/enrich_items.find_unenriched_items` now also treats a row missing either field as needing (re-)enrichment, so a normal cron run backfills old items over time instead of leaving them permanently null — this does mean every previously-enriched item gets one more USDA/LLM round-trip the first time this runs after deploy, a one-time cost accepted for simplicity over a separate one-off backfill script.

Consequence: this is data-layer only. Nothing reads these two fields yet — `ItemNutrition`, the meal-crafting optimizer, and preference scoring are unchanged. Wiring them into actual Soft Preference scoring is a follow-up change once the data has had time to backfill.
