# Expand customizable build-your-own items into fixed-plate protein variants

Cornell's dining feed lists some dishes as a single generic Menu Item with no protein specified — e.g. "Customizable Iron Grill Stir-Fry," which is only ever served as one full plate with a choice of pork, chicken, or tofu mixed in. Treating that name the way every other Menu Item is treated (one Nutrition Match, gram-solved like a scoop of rice — see [[0003-meal-crafting-algorithm]]) is wrong on both counts: its macros depend entirely on which protein is chosen, and the dining hall never serves a partial or oversized portion of it.

We considered adding a single "average stir-fry" Nutrition Match for the raw name, but that bakes in an arbitrary protein assumption (and a wrong one for anyone with a diet restriction — a vegetarian would have no way to know the averaged number silently included meat). We also considered a generic "combo item" schema (sub-items, quantities, a join table), but nothing else in the feed currently needs that shape, and per the project's simplicity bias we'd rather add it when a second real case shows up than design it against one example.

Decision: `app/services/customizable_items.py` holds a small registry mapping a raw Menu Item name to its protein variants and a fixed whole-plate gram weight. Everywhere a raw name is looked up for enrichment (`app/jobs/enrich_items.py`) or candidate generation (`app/routers/crafted_meals.py`), it's expanded first into `"<name> (Pork)"`, `"<name> (Chicken)"`, `"<name> (Tofu)"` — a no-op for every ordinary item. Each variant gets its own Nutrition Match and Diet Tag from the existing enrichment pipeline, so a vegetarian's Hard Constraint naturally leaves only the Tofu variant eligible, with no special-casing in the optimizer itself.

`ItemNutrition` gained one field, `fixed_serving_grams`, set only for these variants. `solve_portions` (`app/services/meal_crafting.py`) appends any fixed-serving item at that exact weight before anchor selection runs, deducts it from the target, and never gram-solves it — the anchor/side logic is otherwise unchanged. Which of the three variants actually gets recommended falls out of the existing pipeline unmodified: `generate_item_sets`'s per-category rotation puts each variant in its own candidate, [[0009-deterministic-preference-preranking]] ranks them by the user's liked/disliked tags, and the LLM polish step makes the final pick — the same way it picks between any other two Menu Items today.
