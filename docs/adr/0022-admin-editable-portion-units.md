# Let the admin override a food's portion unit, stored separately from its NutritionMatch

[[0016-admin-panel-for-nutrition-corrections]] kept portion size read-only in the admin panel: the unit + grams-per-unit a food is pictured in ("1 palm = 85g", "1 scoop = 95g") came only from the keyword heuristic in `frontend/foodDensity.ts`, so fixing a bad mapping meant a code change and a frontend deploy. In practice the heuristic's misses are per-food, not per-rule — "Chicken Noodle Soup" matching `noodle` → scoop before `soup` → cup, or a dish name with no keyword at all falling back to 300g "plate" — and reordering or widening a keyword rule to fix one food routinely shifts others. The operator spots these one at a time while reviewing foods in the panel, which is exactly where a fix should be one click away.

This changes what [[0016-admin-panel-for-nutrition-corrections]] decided about portions only; it does not touch [[0007-nutrition-per-100g-portion-deferred]]. A portion unit is a *display* mapping — how a gram count the optimizer already chose gets pictured and stepped through in the UI — not a serving size. Nutrition stays per 100g, `meal_crafting.py` never reads it, and logged-meal nutrition is still recomputed server-side from grams × per-100g density ([[0004-tracking-scope]]).

Alternatives considered:

- **Columns on `NutritionMatch`.** Rejected: `NutritionMatch` is documented and named as a density, never a portion, and `app.jobs.enrich_items.save_result` owns that row's lifecycle (it upserts the whole row on re-enrichment — the known gap noted in 0016). Keeping the override in its own table means re-enrichment can never clobber it, and the "density, not portion" invariant stays obvious from the schema.
- **Ship the override inline on every item payload** (`/menus/today`, crafted meals, logged meals). Rejected: four response shapes plus the crafted-meals cache ([[0017-crafted-meals-caching]]) would all need to carry and invalidate it, for data that's a handful of rows. Every frontend call site already resolves units by item name through `getPortionUnit`, so one small name-keyed map is the narrower seam.
- **Editing the keyword rules themselves from the panel.** Rejected: rule order is load-bearing (first match wins), so a data-editable rule list makes every edit a potential regression across hundreds of foods. Per-food overrides can't affect any food but the one edited.

Decision: a new `PortionOverride` table (`app.db.models.PortionOverride`), keyed by `item_name` like `NutritionMatch`/`DietTag`, holding `unit` (one of the existing seven `PortionUnit`s) and `grams_per_unit`. The admin panel's food editor gains a "Portion" section with its own save and a "Reset to default" action (`PUT`/`DELETE /admin/api/foods/portion`), separate from the macro save so editing macros never accidentally freezes the heuristic's current answer as an override. A public `GET /portion-overrides` returns the full name → `{unit, grams_per_unit}` map; the frontend loads it once at boot and `getPortionUnit` consults it before falling back to `UNIT_RULES`. A failed fetch just means every food uses the heuristic, same as before this change. `app.services.portion_display` applies the same precedence so the admin panel shows what the app actually uses.

The unit vocabulary stays the fixed seven units (`frontend/foodDensity.ts`'s `PortionUnit`), mirrored by hand in `app.services.portion_display` as before — free-text units would need their own singular/plural labels and rounding granularity, which isn't worth it until a real food needs one.
