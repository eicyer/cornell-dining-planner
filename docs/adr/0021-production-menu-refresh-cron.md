# Refresh production menu data via a Railway cron service, not the local Mac

Production (the Vercel-fronted, Railway-hosted deployment at `cornell-dining-planner-production-0c3b.up.railway.app`) went dark for every eatery — `GET /menus/today` returned an empty `menu_events` list for all ten dining halls, which `app.routers.crafted_meals.closed_reason` correctly renders as "Closed today." Root cause: production's database hadn't been scraped since 2026-08-30. `scripts/daily_refresh.sh` and its launchd plist (`scripts/com.cornell-dining-planner.daily-refresh.plist`) — the only recurring automation in this repo — read `DATABASE_URL` from `.env.local`, which points at the developer's local Postgres (`localhost:5433`). They have never touched production. Production's data has only ever been populated by someone SSHing in and running `scrape_menus` → `enrich_items` → `craft_daily_meals` by hand, which is what restored it this time too. A schema migration (adding `common_foods`) was found stuck the same way — `alembic_version` on production was behind head with no mechanism to catch it up short of the same manual SSH.

We considered triggering the refresh from GitHub Actions on a schedule, calling a new authenticated admin endpoint that kicks the jobs off server-side. Rejected: `enrich_items` alone took over ten minutes against a cold cache of unenriched items (307 USDA/LLM calls), which doesn't fit inside a synchronous HTTP request, and running it as a fire-and-forget background task from a web request risks silently dying with the request/worker rather than surfacing a failure anywhere. It also means a new public(-ish) trigger surface to gate correctly, for no benefit over Railway's own primitive for exactly this.

Decision: a second Railway service, `cornell-dining-planner-refresh`, in the same project/environment as `cornell-dining-planner`, connected to the same GitHub repo and the same `backend/Dockerfile` — no new build config, no dependency drift between "the API" and "the scraper," since it's the same image. It differs only in:

- **Start Command**: `sh scripts/refresh_production_menus.sh` (new — runs the same three jobs, in the same order, that `scripts/daily_refresh.sh` already documents the ordering contract for, minus the `docker compose up -d` / `.venv` bits that only make sense on a local Mac).
- **Cron Schedule**: `0 9,15 * * *` (UTC; ~5am/11am Eastern during EDT). Two chances a day for the same reason `com.cornell-dining-planner.daily-refresh.plist` already gives three chances locally — every job in the pipeline is idempotent (docs/adr/0002, 0003, 0017), so a redundant run costs nothing beyond a few no-op DB queries and some wasted USDA/LLM calls on items that turn out to already be enriched.
- **Variables**: reference the existing secrets via Railway's `${{ServiceName.VAR}}` syntax (`DATABASE_URL` from the Postgres service, `USDA_API_KEY`/`ANTHROPIC_API_KEY` from `cornell-dining-planner`) rather than duplicating them onto a second service that would then need to be kept in sync by hand.

This is a direct infrastructure analog of [[0019-precompute-crafted-meals-for-every-period]]'s own local fix: that ADR already diagnosed "a plain crontab entry doesn't reliably run because it can't wake a sleeping Mac" and moved local refresh to launchd for several-chances-per-morning resilience. The insight generalizes one step further here — a laptop being on and awake was never something production's data freshness should have depended on in the first place, launchd or not. Railway's own scheduler removes that dependency entirely.

Also fixed as part of the same root cause: `cornell-dining-planner`'s deploy config gained `preDeployCommand: alembic upgrade head` (previously unset). Railway runs this once before cutting a new deploy over, in the same network/environment as the service, so future migrations ship automatically with the next deploy instead of requiring the same manual-SSH catch-up this session needed for the Common Foods migration.

## Known limitation

Two fixed UTC times don't track US Eastern's DST transitions, so the effective local run times drift by an hour twice a year (5am/11am Eastern in summer, 4am/10am in winter) — cosmetic, since dining menus don't change meaningfully within that window either way. Revisit only if a use case ever needs the refresh pinned to a specific local wall-clock time.
