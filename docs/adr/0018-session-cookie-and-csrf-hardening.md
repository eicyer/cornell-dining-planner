# Harden session cookies and add CSRF defense-in-depth before first deploy

Auth is Google OAuth (`app.routers.auth`) landing in a Starlette `SessionMiddleware` cookie (`request.session["user_id"]`), and `frontend/api.ts` sends every request with `credentials: 'include'`. Combined with `CORSMiddleware`'s `allow_credentials=True`, this is the textbook setup for CSRF: any state-changing request that reaches the backend with the session cookie attached gets treated as authenticated, regardless of what page triggered it. Until now nothing defended against that beyond whatever `SameSite` default Starlette happens to ship (`lax`), and the session cookie itself had no explicit `secure`/`max_age` handling and was never rotated on login.

We considered three ways to close the CSRF gap:

- **Do nothing beyond `SameSite=Lax`.** Rejected as too thin to rely on deliberately: `SameSite=Lax` already does most of the real work for top-level navigation, but it doesn't cover every case (some older browsers, and it's a browser-vendor default we don't control the ceiling on) and the app was running on Starlette's default without ever pinning it explicitly, so a future dependency bump could silently change behavior.
- **A full double-submit CSRF token system** (server-issued token echoed in a header, verified per-request), the conventional pattern for form-based apps. Rejected as disproportionate: the app has exactly four mutating surfaces (`preferences`, `crafted_meals`/`logged_meals` logging, and the single `PUT /admin/api/foods/detail` — [[0016-admin-panel-for-nutrition-corrections]]), all JSON APIs called via `fetch`, none of them classic HTML `<form>` posts. A token system adds a state-management burden (issue, store, attach, rotate) for a threat an `Origin` check already covers at this app's scale.
- **An explicit `Origin` allowlist check on unsafe methods** (`app.core.csrf.CSRFOriginCheckMiddleware`), layered on top of `SameSite=Lax` rather than replacing it. Chosen: cheap, stateless, and matches the actual shape of the traffic — every legitimate mutating request already originates from either the Expo frontend (`Settings.cors_allowed_origins`) or the same-origin admin panel (`Settings.backend_url`, since [[0016-admin-panel-for-nutrition-corrections]] serves `/admin` same-origin deliberately). Anything else gets a 403 before it reaches a route handler.

Decision: `SessionMiddleware` now sets `same_site="lax"` explicitly (not relying on the default), `https_only=(settings.environment == "production")` so cookies aren't marked `Secure` over local HTTP but are once `ENVIRONMENT=production` ([[0017-crafted-meals-caching]] is unrelated, this is the config-foundation ADR referenced from `app.core.config`), and a bounded `max_age` of 14 days instead of "until the browser closes." `app.routers.auth.auth_callback` now calls `request.session.clear()` immediately before writing `user_id`, so any session state that existed before authentication (fixation risk) doesn't survive login. `CSRFOriginCheckMiddleware` rejects `POST`/`PUT`/`PATCH`/`DELETE` requests whose `Origin` header isn't in `cors_origins ∪ {backend_url}`; `GET`/`HEAD`/`OPTIONS` are untouched since they're not expected to mutate state.

Open item for whoever executes the eventual deploy ([[0016-admin-panel-for-nutrition-corrections]]'s "same origin" reasoning applies here too): put the frontend and backend on the same registrable domain (e.g. `app.<domain>` / `api.<domain>`) rather than unrelated domains, so `SameSite=Lax` continues to do real work in production the way it does for `localhost` today. This is a deployment-topology decision, not code, and is called out explicitly so it isn't decided ad hoc when the Railway/Render deploy actually happens.
