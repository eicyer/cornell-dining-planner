# Add a per-eatery Station Survey, sourced live from the menu, alongside the hand-curated Food Preference Survey

[[0011-food-preference-survey]]'s 10-round survey is a one-time onboarding step from a fixed, hand-curated catalog of Cornell-wide item names — good for a cold-start signal, but static forever after: it can't tell the app "at Morrison specifically, I'd rather have the chicken than the salmon today." Building that from real usage patterns would mean identifying which items *recur* together at a given eatery (the "same 3-4 Grill options every day" intuition) — but that requires data the system doesn't have and isn't close to having: `app/jobs/scrape_menus.py::replace_menu_items` fully deletes and re-inserts a `MenuEvent`'s `MenuItem` rows on every run, so no history of past days' menus exists, and there's no scheduler running the scrape at all (both jobs are manual, per their docstrings) — recurrence would only become knowable after adding both a scheduler and a schema change to retain history, then waiting for enough elapsed days to matter.

We considered building that (a scheduler + a history table + a frequency query) since it directly answers "what recurs," but it's a materially bigger lift for the same practical outcome as a smaller alternative: [[0011-food-preference-survey]] itself already established that dining-hall station names (Grill, Pizza, Chef's Table) are a stable, recurring *concept* even without historical proof of which specific dishes repeat — [[0012-plate-role-portioning]] independently confirmed these station categories exist consistently across eateries by querying live menu data. So instead of deriving "what recurs" empirically, we take today's actual snapshot at *this* eatery, restricted to those staple stations, and ask the same pairwise "which would you rather eat" question [[0011]] already validated — sourced live instead of hand-curated, per-eatery instead of Cornell-wide, repeatable instead of once.

Decision: `app/services/station_survey.py::build_station_survey(eatery_id, items, diet_restrictions, allergens)` builds pairs from whatever's actually on the menu today at one eatery, restricted to `STAPLE_STATIONS` (`grill`/`flat top grill`/`iron grill`, `pizza`/`pizza station`, `chef's table` — lowercased category-name sets, same idiom as [[0012-plate-role-portioning]]'s `EXCLUDED_ROLE_CATEGORIES`), at most `MAX_PAIRS_PER_STATION` (2) pairs per station. Confirmed live against real menu data: Cornell's own category feed mixes a sauce into "Flat Top Grill" alongside real dishes (a "Green Tahini Sauce" was about to get paired against a salad as if it were a comparable choice) — the exact same station-name-isn't-a-food-role problem [[0012]] diagnosed, so `station_survey.py` reuses `meal_crafting.CONDIMENT_KEYWORDS` directly rather than re-deriving its own condiment list.

Each live item's taste tags are derived deterministically from its own name (`_derive_tags`: lowercase, strip a small stopword list, keep significant words) rather than hand-curated or LLM-tagged — this runs on every eatery-detail view, not a one-time onboarding step, so it stays free and instant, consistent with the project's general preference for a deterministic floor over an LLM dependency where one will do ([[0009-deterministic-preference-preranking]]'s same argument). Confirmed this produces sensible signal live: comparing "Grilled Chicken Breast" vs. "Grilled Salmon" nets `chicken`/`breast` as liked and `salmon` as disliked — the shared word "grilled" cancels to net-zero and is dropped, isolating what's actually distinctive between the two options without any special-casing.

Because there's no server-side survey state kept between the GET and the POST (matching [[0011]]'s existing determinism contract for the exact same reason — "pair_id + choice must resolve the same way regardless of when GET ran vs POST"), `build_station_survey` must be — and is — deterministic given the same `(eatery_id, items, diet_restrictions, allergens)`: items are deduped and sorted by name before pairing, so the POST handler can re-derive the identical pairs from scratch and resolve `pair_id`s against them. `app/services/food_survey.py::score_survey` gained an optional `pairs_by_id` parameter (defaulting to its existing hand-curated catalog, so every existing caller is unaffected) so the scoring logic — net +1/-1 per tag, skip is a no-op, tie drops the tag — isn't duplicated for a second pair source; `merge_tags` is reused unchanged.

New endpoints `GET`/`POST /preferences/station-survey/{eatery_id}` live in `app/routers/preferences.py` alongside the existing food-survey endpoints (same "feeds `liked_tags`/`disliked_tags`" purpose), but are architecturally separate from [[0011]]'s onboarding survey: repeatable at any time, scoped to one eatery, and never touches `UserPreference.food_survey_completed`. Both survey types write into the exact same `liked_tags`/`disliked_tags` fields via the same `merge_tags` union — `app/services/preference_scoring.py` needed no changes to pick up this signal, matching [[0009-deterministic-preference-preranking]]'s existing contract exactly.

## Known limitation: still doesn't answer the original "what recurs" question

This answers "what do you prefer among today's options at this eatery," not "what does this eatery typically serve" — a user visiting on an atypical day gets pairs from that day only. The historical-recurrence approach considered and set aside above would answer a genuinely different question and remains a larger, separate undertaking (scheduler + history retention) if that specific need shows up later.
