# Add an Eating Style registry instead of one bespoke field per new preference category

Adding "eat less refined sugar," "keto," "high protein," "emphasize whole foods," and "emphasize fiber" as user preferences the same way `prefer_whole_foods` was added — one bespoke boolean/enum per category, threaded by hand through the model, the preferences router, and whichever of [[0003-meal-crafting-algorithm]]/[[0009-deterministic-preference-preranking]]/`app.services.tdee` it touches — doesn't scale. Diet restrictions are worse still: their vocabulary requires every menu item to carry an LLM-inferred tag from [[0002-enrichment-pipeline]], a mechanism that fits an exact-match category like "vegan" but not a numeric-threshold one like "low sugar."

We first considered a single flexible "preset bundle" abstraction — a named config combining an optional target-shaping delta, an optional selection-time constraint, and a ranking weight, so any future category could be added as one registry entry regardless of which mechanism it needs. Decided against it for now: every category on the current list needs only one of two mechanisms, not three, and building a generic constraint-delta system with no current user is exactly the kind of speculative abstraction this codebase avoids elsewhere. Revisit if a future category genuinely needs to also filter food selection, not just shape targets or rank candidates.

Decision: split the list along the two mechanisms that are actually needed today.

- **Target-shaping** (keto, high_protein): two new `MacroStyle` values (`app.db.models.MacroStyle`), extending the existing balanced/lower_carb mechanism rather than inventing a new one. `app.services.tdee` gains a per-style non-carb-calorie cap (`MAX_NON_CARB_KCAL_FRACTION_BY_MACRO_STYLE`) so keto's carb target can actually reach keto-range (previously every style shared one 85%-cap "no extremes" guardrail that would have kept even a nominal "keto" option moderate), and a per-style protein-per-kg boost for high_protein layered on top of the existing goal-driven value.
- **Soft-rank-only** (low_sugar, high_fiber, whole_foods_focus): a new `eating_styles: list[str]` column on `UserPreference`, validated against `app.services.eating_styles.EATING_STYLES` the same way `diet_restrictions`/`allergens` validate against their own vocabularies — but, unlike those two, never enforced as a filter. `app.services.preference_scoring` gains one rule per style, scored the same +1/-1-per-item way liked/disliked tags already are. `prefer_whole_foods` is retired in favor of `"whole_foods_focus" in eating_styles` — one mechanism instead of two for what was always the same kind of preference. low_sugar/high_fiber read real `sugar_g_per_100g`/`fiber_g_per_100g` data ([[0014-sugar-fiber-tracking]]) against externally-defined thresholds (UK FSA's 22.5g/100g "high sugar" line; the FDA's ~10%-DV "good source of fiber" convention, adapted to this app's per-100g basis) rather than a keyword heuristic.

This was also the point at which we explicitly decided eating styles never exclude a candidate outright, even for a style as strict as keto in principle — consistent with [[CONTEXT.md]]'s Soft Preference definition and [[0009-deterministic-preference-preranking]]. A near-zero carb target from the keto MacroStyle is reached through target-shaping plus the carb-role-skip fix in [[0012-plate-role-portioning]], not through a hard filter on carb-containing items.

Consequence: adding a purely soft-rank category later (e.g. "high calcium") is a two-line change — one entry in `EATING_STYLES`, one rule in `preference_scoring.score_candidate`. Adding another target-shaping category is a new `MacroStyle` value plus whatever `tdee.py` constants it needs, the same shape as this change. Neither requires a new subsystem.
